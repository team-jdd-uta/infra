# Secret Management Follow-Up

## Current State

Team9 uses AWS Secrets Manager as the runtime secret source and External Secrets Operator to project selected values into Kubernetes Secrets.

The current setup has two patterns:

- Terraform manages both the secret resource and generated value for infrastructure-derived credentials.
- Operators manually inject application or third-party values into Secrets Manager, while GitOps `ExternalSecret` resources consume them.

## Recommended Target Pattern

Use this split for operational consistency:

- Terraform manages Secrets Manager metadata: name, tags, description, KMS key, and recovery policy.
- Terraform does not manage human/operator-provided secret values.
- External Secrets Operator projects values from Secrets Manager into Kubernetes.
- Reloader restarts workloads when projected Kubernetes Secret values change.

This keeps secret inventory reproducible without storing third-party credentials, Slack webhooks, Git tokens, or passwords in Terraform state.

## Follow-Up Steps

1. Add `aws_secretsmanager_secret` resources for the manually-managed secrets.
2. Import existing AWS Secrets Manager secrets into Terraform state.
3. Do not add `aws_secretsmanager_secret_version` for operator-provided values.
4. Run `terraform plan` for the owning layer until it reports no infrastructure drift.
5. Document the required JSON schema for each secret in this file or service READMEs.
6. Rotate any credential that has been pasted into chat, logs, or local shell history.

## Bootstrap After Destroy/Apply

After a full destroy/apply, operators must repopulate secret values before workloads that consume them can become healthy.

Use a controlled bootstrap script or CI secret-injection job that writes values to Secrets Manager without printing them to logs.
